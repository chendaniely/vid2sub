# vid2sub: kickoff Q&A

Dan's answers to the questions asked while adopting plan-driven-development (skill 65072f9) in
this repo, which predates the skill. M1 was built and merged (#2) before it. Each item gives the
scenario as asked, the options, and the answer with Dan's reason in his own words; where he gave
none, it says so.

### 18. The kickoff council's Critical: the sidecar race (2026-10-24)

**Scenario:** in `vid2sub serve`, Dan presses Save just as a job on the Jobs page writes the
same episode's sidecar (or a CLI run does). The compare-and-swap leaves a window between its
re-check and the file's replace, so one writer's records can vanish while the editor still says
"saved" (kickoff council, reliability finding 1). What do you expect?

- **A. Lock + re-check** (recommended): inside the app, one lock per sidecar, by its real path,
  around every write; the re-check moves to just before the rename, as §14.6 says, so a CLI run
  beside the app leaves only a sub-millisecond window, written into §18.3. Built in Phase 2 Task
  6, with a guard test that fails today.
- **B. Also a lock file** next to each sidecar that every writer takes: closes the window fully,
  but a crash holds Saves up for about 30 s, SMB's locking is unreliable, and §6.5 gains a file.
- **C. In-app lock only;** §18.3 says running both at once is not fully safe.

**Answer:** A. **Reason:** none given; Dan chose the recommended option.

### 19. The kickoff council's Critical: a restored crash draft loses edits to new cues (2026-10-24)

**Scenario:** Dan inserts a cue and types its line, splits another and fixes one half, then the
tab crashes. On reopening he presses Restore. The replay gives the new cues new random ids, so
the typed line and the fixed half are refused and lost; a second tab on the same episode shares,
and clears, the same draft (kickoff council, reliability findings 2 and 3). What do you expect?

- **A. The page proposes ids** (recommended): split, merge and insert carry the new cue ids the
  page proposes; the server checks their shape and that each is free, so a replay is exact. The
  draft is cleared only after a replay with no refused step. Each tab keeps its own draft (a tab
  id in `sessionStorage`), offered with its time. Built in Phase 2 Tasks 2, 15 and 16, with an
  e2e test that inserts, splits and merges, crashes and restores.
- **B. Map ids on replay:** no change to the edit messages; it depends on each step creating its
  ids in a fixed order. Per-tab drafts as in A.
- **C. List what failed** after a restore, for Dan to redo by hand. Per-tab drafts as in A.

**Answer:** A. **Reason:** none given; Dan chose the recommended option.

### 24. Safari's downloaded Save (2026-10-25)

**Scenario:** in Safari's Pages editor Dan fixes a line and Saves, which downloads the sidecar and

  flag to §18.1.
- **B. Warning only,** no new flag.
- **C. As planned:** replace the old files.

**Answer:** A. **Reason:** none given; Dan chose the recommended option.

### 26. How a release updates the site (2026-10-25)

**Scenario:** Dan pushes tag v0.2.0; `release.yml` publishes the release, and the Pages site's
install index must then be rebuilt, but a release made with GITHUB_TOKEN starts no
`release: published` workflow. As planned (Phase 4 Decision 2), `pages.yml` follows `release` by
`workflow_run`, which needs three guard conditions, a naming rule (Decision 22) and an
expression evaluator in its tests (kickoff council, simplicity 4). What do you expect?

- **A. Dispatch it** (recommended): `release.yml`'s publish job ends with
  `gh workflow run pages.yml --ref main`; `pages.yml` loses `workflow_run`, its three conditions,
  Decision 22 and their tests; the publish job, which runs no repository code, gains
  `actions: write`. If the dispatch ever fails, the release stands and Dan runs `pages.yml` by
  hand. Decision 2 and §23.3 say so.
- **B. By hand** after each release.
- **C. As planned:** `workflow_run`.

**Answer:** A. **Reason:** none given; Dan chose the recommended option.
